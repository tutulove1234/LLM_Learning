
# 控制代码修改范围
原则：收拢上下文、明确边界限制、分步小步执行
1. 明确设定“负向约束”与“不动范围”，在提示词中明确加上“禁止清单”。
  例如：
  1. 限定修改区域: “只修改handleSubmit 函数内部的校验逻辑，请勿重构其他函数或更改组件状态结构。”
  2. 保护公共接口：“不要修改任何函数签名、入参名、返回类型和公共对外暴露的API。”
  3. 禁止重写和风格调整：“保持现有的命名风格和代码格式，不要引入新的第三方依赖，不影响顺便重命名未提及的变量。”
2. 要求输出Diff或局部代码片段，而非整文件覆盖
3. 将任务拆解为两步：“先分析计划，确认后再出代码”
  直接让AI编码容易导致它理解偏差并一次性破坏大片代码。
  * 第一步：“请先列出修改思路以及具体需要改动哪几个函数/文件，不要直接输出代码。”
  * 第二步（根据其思路补充/剔除不需要的改动后）：“思路没问题，现在请仅针对第2点编写实现。”

# 控制文档生成的精准性（防止洋洋洒洒、假大空）
1. 给出“空骨架/模板”，让AI做填空题
避免“请帮我写一份xx接口的设计文档”（AI会生成几页背景介绍、未来展望等客套话）。
* 直接给模板：

```text
请按照一下固定结构输出，不要添加其他未列出的章节：
## 变更目的（1~2 句话）
## 接口入参 & 返回值（表格形式）
## 边界异常说明（Bullet points）
## 影响范围与迁移注意事项
```

2. 设定字数与行数硬性上限
* “结论与背景说明请控制在100字以内。”
* “请直接给出要点列表（Bullet points），每条不超过一行，严禁任何前言、客套话和总结段落”

3. 明确受众与场景
* 精准指向：“受众是熟悉本项目的资深后端开发，请直接讲核心技术方案和关键字段含义，跳过通用的基础概念解释。”

# 工程化与工具级技巧
1. 善用规范文件（Rules/System Prompts）：在项目中创建规范提示词（例如.cursorrules、AGY Rules或工作流规则），内置一条全局铁律：
“除非用户明确要求重构，否则在修改代码时必须遵循最小改动原则（Minimal Diff Principle），严禁擅自修改未被提及的代码。”
2. 结合版本控制做防御性审查：无论AI建议了什么，始终利用Git的局部暂存（如 `git add -p` / IDE 的行级Diff 审查），只挑拣需要的改动，不要盲目全盘接收。
3. 技能（Skills）/ 自定义工作流---用于特定任务或流程，在需要特定深度能力或多步骤操作时加载。



## 创建SKILL流程

1. 在你的项目根目录下创建 .agents/skills/<技能名称>/，如果需要未特定的agent创建也可以 `.claude/skills` `.opencode/skills` 

2. 编写 SKILL.md

   格式为 Markdown + 顶部 frontmatter，vLLM 里的技能全部是这个结构:

   ```markdown
   ---
   name: My Skill
   description: 一句话说明这个技能做什么、什么时候用。这是模型判断是否触发技能的唯一依据，要写清楚触发场景。
   ---
   
   # 技能标题
   
   ## Workflow
   
   1. 第一步做什么
   2. 第二步做什么
   3. 注意事项和禁忌
   ```

   关键点：

   - description 最重要：模型只看到ID、名称和description来决定是否加载技能。

     要把“什么场景该用/不该用”写进去（参考vLLM的check-api-compat，连“不要用于哪些场景”都写了）。

   - 技能ID由路径决定：skills/my-skill/SKILL.md 的ID 是my-skill（frontmatter里的name只是显示名）。建议用小写kebab-case，和目录名保持一致。

   - 路径是相对的：SKILL.md 里引用的脚本、文件路径都相对于SKILL.md所在目录。

   - 附带文件不会自动加载：模型只读到正文，脚本/参考文件要在正文里指路，让模型按需去读。

3. 如果只是项目级通用说明（不是任务技能）

   如果想像 AGENTS.md 那样给所有会话加全局规则，而不是针对某类任务的技能，用 AGENTS.md（放在项目根目录）或 opencode.json 的 instructions 字段更合适。

   技能 适合“特定类型任务的可复用流程”，AGENTS.md 适合“所有工作都要遵守的规范”。

4. 验证

   启动 opencode 后可以直接测试：

   - 在提示里用 @my-skill 显式加载；
   - 或者描述一个匹配 description 的任务，看模型是否自动调用。

5. 可选进阶

   | 需求                       | 做法                                                         |
   | -------------------------- | ------------------------------------------------------------ |
   | 隐藏某技能不让模型自动调用 | frontmatter 加 metadata.opencode/autoinvoke: false， 仍可通过 @ID 手动加载 |
   | 团队共享/跨项目复用        | 放到 ~/.config/opencode/skills（全局），或在opencode.json 的 skills 数组加自定义路径甚至HTTP目录 |
   | 控制权限                   | opencode.json 里配 permissions 的 skill 规则（allow/ask/deny） |



__注：__ `@` 只是显式触发加载；不加 `@` 时模型可能自动触发，前提是description 写得让它觉得相关。没有 description 的技能不会被列入自动提交给模型的列表中。模型永远无法自动发现它。但仍可用 `@` 来显式手动加载。

## SKILL的验证方法和实操建议

### 验证方法

直接问模型“有哪些可用技能”，或看会话开头的 <available_skills> 块，那个列表就是“默认会考虑使用”的全部技能；而实际加载了正文的，会在对话中以 <skill_content> 块出现。

### 实操建议

想让某个技能 “默认更容易被用上”，关键是把 description 写成 “什么时候该用我” 的精准描述就（含正/反例场景），而不是指望默认加载机制。

## 创建Rule的流程

规则文件 Rules 可以全局/项目自动注入。AI在每次收到请求时，后台会自动静默加载这些规则，你无需在每次对话中重复输入。

1. 常见的规则文件位置

   * Antigravity 举例：
     * 全局规则：在用户主目录 `~/.gemini/antigravity/rules` 下创建 .md 文件（所有项目共享）。
     * 项目局部规则：在项目根目录的 `.agents/rules/` 或 `.gemini/rules/` 目录下创建。
   * 其它常见IDE工具（如 Cursor/Copilot）：
     * 项目根目录下的 `.cursorrules` 或 `.github/copilot-instructions.md` 。

2. 编写规范

   可以在项目根目录或全局规则目录下建一个 code-and-doc-constraints.md 

   ```markdown
   # 行为准则：最小改动与精准输出原则
   
   ## 1. 代码修改约束（严格遵循最小改动原则）
   - **禁止过度重构**：除非用户明确要求重构，否则严禁修改任何未被要求的代码、注释或代码风格。
   - **保护对外接口**：严禁更改现有的公共函数签名、入参名称及返回值类型。
   - **输出格式**：修改已有代码时，仅输出需要变更的函数或代码段（或输出Unified Diff），不要输出整个为变动的文件。
   - **依赖保护**：禁止随意引入未经用户同意的第三方库或依赖包。
   
   ## 2. 文档输出约束（精炼与直接）
   - **零客套话**：引进输出前言、客套话、冗长的总结段落。
   - **结构化输出**：默认优先使用Markdown表格、要点列表（Bullet points）。
   - **篇幅控制**：单点说明控制在1~2句话以内，直奔主题，避免泛泛而谈的宏观背景介绍。
   ```

   



# 两者如何配合使用

| 机制           | 适用内容                                                     | 触发方式                                                     |
| -------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Rules（规则）  | “不要乱改无关代码”、“文档别说废话”、“使用TypeScript严格模式” | **完全静默生效**，你日常提问 `帮我修一下这个报错`，AI 就会自动受控 |
| Skills（技能） | “PR审查标准流程”、“系统架构设计文档生成模板”                 | **按意图匹配或手动指定**，处理复杂多步骤的专业任务。         |



建议起步做法：直接在你的根目录或全局规则目录中建一个**规则文件（Rule）**，将代码和文档约束放进去。这样以后日常只需 “把这里的超时时间改成5s”，AI就不会再顺手把整个文件重构一遍了。



# Q&A

* 哪些技能会出现在那个自动提交给模型的列表中？

  Agent从所有来源发现的所有技能（未被权限过滤、未设置如 opencode/autoinvoke: false、有description 的）。

  读取位置（自动发现），文件名称SKILL.md

  * 技能清单（Skills）：按意图/按需加载的专家指令

  | 范围     | 位置                               |
  | -------- | ---------------------------------- |
  | 全局     | ~/.config/opencode/skills          |
  | 全局兼容 | ~/.claude/skills、~/.agents/skills |
  | 项目     | .opencode/skills                   |
  | 项目兼容 | .claude/skills、.agents/skills     |

  项目级来源会从当前目录向上逐级搜索到项目根，每一级命中的目录都会被收录（所以monorepo的子项目也可以有自己的技能）。

  此外，opencode.json(c) 里 skills 数组配置的额外路径/HTTP 目录也会加入。

  * 规则文件（Rules）：自动注入的全局“宪法”

  | 范围     | 位置                             |
  | -------- | -------------------------------- |
  | 全局级   | ~/.gemini/antigravity/rules/*.md |
  | 全局兼容 | ~/.claude/rules、~/.agents/rules |
  | 项目     | .gemini/rules/\*.md              |
  | 项目兼容 | .agent/rules/\*.md               |

  

  

  

* 加载优先级（ID 冲突时）?

  按从低到高注册，后注册的覆盖先注册的（按ID覆盖）：

  1. 内置技能
  2. .claude/skills（全局 -> 逐级向当前目录）
  3. .agents/skills （全局 -> 逐级向当前目录） <- vLLM 用的就是这个
  4. ~/.config/opencode/skills
  5. 项目 .opencode/skills
  6. skills 配置里显式添加的来源



**注：** 超过10行的规则应该下沉为 skill：法条太多太杂，等于没有法。

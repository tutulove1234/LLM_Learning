## 1. GDS 解决什么问题

**GDS（GPUDirect Storage）的核心作用，是让存储设备与 GPU 显存之间通过 DMA 传输数据，尽量绕过 CPU 内存中的中转缓冲区。** 应用仍在 CPU 上调用 cuFile API，CPU 仍参与文件访问和传输控制，但数据可以直接进入或离开 GPU 显存。

传统读入流程：

```text
存储 -> CPU 内存中转缓冲区 -> 复制到 GPU 显存 -> GPU 计算
```

GDS 直接读入流程：

```text
CPU 发起 cuFileRead 并完成控制路径准备
存储端 NVMe / NIC 的 DMA 引擎 -> GPU 显存 -> GPU 计算
```

写出方向与之对应：GPU 产生数据后，由存储附近的 DMA 引擎从 GPU 显存取数并写入存储。

| 对比项 | 传统 POSIX I/O 与显式 GPU 复制 | GDS / cuFile |
| --- | --- | --- |
| 应用传入的目标缓冲区 | `pread/pwrite` 使用 CPU 内存缓冲区 | 可以直接指定 GPU 显存缓冲区 |
| 数据搬运 | 通常先经过 CPU 内存，再进行 CPU/GPU 复制 | 条件满足时走存储与 GPU 之间的直接 DMA |
| CPU 的作用 | 控制 I/O，并参与内存中转 | 仍承担控制路径，减少数据中转负担 |
| 预期收益 | 可能受 CPU 内存带宽和额外复制限制 | 降低延迟、缓解带宽瓶颈、降低 CPU 负载 |
| 实际效果 | 受存储、链路及并发影响 | 同样受拓扑、驱动、文件系统、请求大小与并发影响 |

GDS 更适合计算流水线已迁移到 GPU、数据读入后首先由 GPU 处理、写出前最后由 GPU 处理的场景。原文强调粗粒度、流式传输；对于细粒度随机访问，操作系统调用及内核切换开销仍需摊薄。显式传输所用缓冲区需能容纳在可用 GPU 物理显存中。

**理解边界：** 调用了 cuFile，并不代表每次 I/O 都是零拷贝或完全绕过 CPU 内存。兼容模式、对齐处理和动态路由都可能引入中转。

来源：§1.1.2-1.2.1，正文第 2-5 页。

## 2. 主要功能清单

| 功能 | 作用与使用方式 | 关键条件或限制 |
| --- | --- | --- |
| 显式文件读写 | `cuFileRead`、`cuFileWrite` 按文件、偏移、长度及缓冲区地址发起传输，语义接近 `pread/pwrite` | 本指南描述的 API 由 CPU 发起；直接路径需要相应平台和存储支持 |
| 驱动与资源管理 | `cuFileDriverOpen/Close`、属性查询与设置、文件句柄注册/注销、缓冲区注册/注销 | 为 I/O 建立和管理运行环境；资源使用完后应清理 |
| CUDA Stream 异步 I/O | `cuFileReadAsync`、`cuFileWriteAsync`，以及 Stream 注册/注销接口 | 同一 Stream 内遵循顺序，不同 Stream 之间可并发 |
| 计算与 I/O 排序 | 支持“读入后计算”和“计算完成后写出” | 异步提交不等于完成，后续使用数据或释放资源须遵守完成关系 |
| 批处理 | `cuFileBatchIOSetUp/Submit/GetStatus/Cancel/Destroy` 管理一组请求 | Batch 本身具有异步性质，用于摊薄逐次提交的固定开销 |
| 多线程调用 | API 是线程安全的，可由应用组织并发 I/O | GDS 不自动提高应用并发度，链路和设备的充分利用依赖应用设计 |
| 路径选择与分段中转 | 根据平台拓扑选择 PCIe、NVLink 等路径，必要时用 GPU 中间缓冲区 | 多一步中转也可能比跨 CPU 根复合体的路径更快 |
| 动态路由 | 针对网络文件系统，选择更接近存储 NIC 的中转 GPU 或其他路径 | 默认关闭，需要配置存储 NIC 地址及路由策略 |
| 兼容模式 | 使用 CPU 内存中转和标准 POSIX 实现，维持 cuFile 功能可用 | 不具有 GDS 直接路径的性能收益 |
| 多种内存目标 | 支持文中列出的 GPU 内存及固定 CPU 内存分配方式 | 可迁移内存等不支持 GDS P2P 的情况，使用兼容路径和内部缓冲区 |
| 监控与排障 | Ftrace、日志与统计分析 | 通过配置选择日志级别和统计项；具体能力受组件支持范围限制 |

来源：§1.1.2、§1.2.2-1.2.5，正文第 2、6-12 页。

## 3. 应用接入与读写流程

### 3.1 接入生命周期

以下是根据原文 API 分类与示例整理的流程，用于理解调用关系，并非可直接编译的代码或完整 API 规范。缓冲区注册、Stream 注册等步骤应按所选接口和实际使用方式安排。

```text
准备驱动、文件系统和运行配置
  -> 初始化 cuFile，打开目标文件
  -> 通过 cuFileHandleRegister 注册文件句柄
  -> 分配 GPU 缓冲区，按需注册缓冲区
  -> 提交同步 / Stream 异步 / Batch I/O
  -> 确认传输完成，进行计算或使用结果
  -> 等待全部相关操作完成
  -> 注销已注册的资源，释放缓冲区，关闭文件与 cuFile
```

文件路径先映射到挂载点，再由挂载点确定文件系统及其控制路径。`libcufile.so` 根据文件系统、配置和硬件条件决定使用 GDS 路径、兼容路径，以及是否需要内部缓冲区。

### 3.2 读入、计算、写出的顺序

| 阶段 | 操作 | 完成关系 |
| --- | --- | --- |
| 读入 | 从文件指定偏移读取到 GPU 缓冲区 | 使用该数据的 GPU 计算必须在读取完成后执行 |
| 计算 | GPU Kernel 消费输入并生成输出 | 写出操作必须在相关计算完成后执行 |
| 写出 | 把 GPU 缓冲区中的结果写入文件 | 复用或释放缓冲区前，须确认相关 I/O 已完成 |

使用 CUDA Stream 时，可按下列逻辑组织同一 Stream 中的工作：

```text
异步读取 -> GPU Kernel -> 异步写出
```

同一 Stream 内的顺序保证 I/O 与计算之间的依赖；使用多个 Stream，可创造不同任务重叠执行和使用多个 DMA 引擎的机会。原文还说明，I/O 长度、文件偏移和缓冲区偏移可以根据此前 CUDA Kernel 或函数的执行结果，在有效范围内动态变化。

### 3.3 直接路径的判断

```text
应用提交 cuFile I/O
  -> 检查文件系统、挂载点、硬件、驱动和配置
     -> 满足直接传输条件：使用 GDS DMA 路径
        -> 必要时分段、选择中转 GPU 或处理对齐
     -> 不满足条件且兼容模式可用：通过 CPU 内存和 POSIX 路径完成
  -> 返回完成结果或通过异步机制确认状态
```

直接路径通常要求满足 `O_DIRECT` 语义。原文同时给出版本例外：从 CUDA Toolkit 12.2 / GDS 1.7.x 起，即使文件打开时没有指定 `O_DIRECT`，对页对齐的缓冲区、长度和偏移，cuFile 也可以采用 GDS 驱动的 `O_DIRECT` 路径。因此，不能仅用文件是否带有该标志判断实际路径。

来源：§1.2.1、§1.2.2.5、§1.2.3、§1.2.5、§1.3.2，正文第 3-5、10、11-12、17-20 页。

## 4. 软件架构与两条底层流程

### 4.1 各组件的职责

![原文图 1.2：GDS 功能工作流与软件组件](nvidia-gds-overview.assets/gds-workflows.png)

*原文图 1.2，正文第 18 页 / PDF 第 22 页。图中展示用户态、内核态、VFS、厂商驱动及 RDMA 组件之间的关系。该图主要反映 nvidia-fs 与厂商路径，NVMe P2PDMA 的版本例外见第 7 节。*

| 层次或组件 | 主要职责 |
| --- | --- |
| 应用 / 框架 | 引入 `cufile.h`，在 CPU 上调用 cuFile API，组织数据与计算任务 |
| `libcufile.so` | 实现 cuFile API，判断执行模式、处理对齐与内部缓冲，并协调异步操作 |
| `libcuda.so` | 按需配合 cuFile，支持 CUDA Stream 相关操作 |
| `nvidia-fs.ko` | 在依赖该模块的路径中处理 IOCTL，提供 GPU 地址识别、DMA 地址映射等回调 |
| Linux VFS | 根据文件和挂载点进入相应文件系统或块设备栈 |
| Linux / 厂商存储驱动 | 接收 I/O 请求，获取 DMA 所需的地址信息并编程存储端 DMA 引擎 |
| `libcufile_rdma.so`、厂商用户态库、`libibverbs.so` | 支持用户态 RDMA 路径中的信息获取与厂商交互 |
| NVMe / NIC 等设备 | 执行存储与 GPU 显存之间的 DMA / RDMA 数据搬运 |

**控制路径和数据路径需要分开理解：** CPU 上的软件负责请求、映射、调度和完成通知；真正的数据搬运可由设备 DMA 引擎直接完成。即使 PCIe 数据经过 CPU Root Port，也不等于数据进入 CPU 内存。

### 4.2 流程一：经 nvidia-fs 与 VFS 的读写

适用于原文描述的、依赖 `nvidia-fs.ko` 的 `cuFileRead/cuFileWrite` 路径。

1. **应用发起请求。** 应用或框架链接 cuFile，调用 Driver / I/O API，传入文件、偏移、长度和 GPU 缓冲区等信息；用户态库处理对齐相关问题。
2. **cuFile 选择实现。** 根据文件系统、配置与硬件支持，选择 GDS 或兼容模式，并判断是否使用内部 GPU 缓冲区。
3. **用户态库进入内核。** `libcufile.so` 对 `nvidia-fs.ko` 发起相应 IOCTL；Stream 接口按需与 CUDA 用户态驱动交互。
4. **nvidia-fs 向 VFS 发起底层 I/O。** 传入完成回调 `nvfs_io_complete`，VFS 再进入对应文件系统或块存储路径。
5. **存储驱动识别并映射 GPU 地址。** 使用 `nvfs_is_gpu_page` 判断目标是否属于 GPU，通过 `nvfs_dma_map_sg*` 等回调获取 DMA 所需的地址列表。
6. **设备执行数据传输。** 存储驱动根据得到的 GPU DMA 地址编程 NVMe / NIC 等设备的 DMA 或 RDMA 引擎，直接在存储与 GPU 显存之间搬运数据。
7. **完成通知逐层返回。** 块传输完成先通知存储驱动；每轮 I/O 再通过此前注册的回调通知 `nvidia-fs.ko`，完成上层请求。

**关键机制：代理地址。** 该路径用 CPU 系统内存中的代理地址代表 GPU 虚拟地址，让请求能够穿过 Linux I/O 栈，再转换成设备可用的 DMA 总线地址。DMA 引擎并不会把这些代理地址对应的 CPU 内存当作实际数据缓冲区。

**关键机制：scatter-gather list。** 一次 API 调用虽然描述连续的虚拟地址范围，但底层可能被拆成多段物理地址，或分散到多个设备上，例如 RAID-0。驱动最终利用散布/聚集地址列表组织 DMA；一次调用不一定对应一次硬件传输。

### 4.3 流程二：用户态 RDMA 与厂商库

1. **应用调用 cuFile。** 应用或框架通过相同的 Driver / I/O API 发起请求，用户态库处理对齐等事项。
2. **获取 RDMA 信息。** `libcufile_rdma.so` 向 cuFile 提供 key、GID、LID 等 RDMA 相关信息。
3. **与厂商实现交互。** `libcufile.so` 调用相应厂商库回调；Rkey 可以直接在用户态交换，也可以根据厂商实现通过 nvidia-fs 内核回调传递。

两条流程的应用入口都可以是 cuFile，但底层控制路径不同。**不能把所有 GDS I/O 都理解为固定经过同一套 VFS / nvidia-fs 链路。**

来源：§1.3.1-1.3.3，正文第 17-20 页。

## 5. 性能优化与动态路由

### 5.1 原文中的性能优化手段

| 手段 | 为什么有用 | 应用侧需要关注什么 |
| --- | --- | --- |
| 减少 CPU 中转复制 | 降低额外拷贝开销与 CPU 内存带宽压力 | 实际请求是否命中直接路径 |
| 拓扑感知的路径选择 | 避免代价高的跨根端口、跨 CPU 路径 | GPU、NIC、NVMe 的 PCIe / NVLink 关系 |
| GPU 中间缓冲 | 允许先到邻近 GPU，再借助 GPU 间高速链路到目标 GPU | 更短或更宽的路径可能抵消额外复制开销 |
| 多线程 / 多设备并发 | 利用多条链路和多个设备的总带宽 | 并发度由应用组织，线程安全不等于自动并发 |
| 异步与多 Stream | 让 CPU 提交、GPU 计算和 I/O 有机会重叠 | 依赖关系、缓冲区复用和完成时机 |
| 批处理 | 将提交固定开销摊到多个 I/O 请求 | 是否存在可一起提交的一组请求 |

原文说明，小传输更容易体现减少额外复制带来的延迟收益；但这并不改变其对粗粒度流式传输的适用性定位。吞吐和延迟应分别结合请求大小评估。

### 5.2 动态路由的工作过程

![原文图 1.1：PCIe、NVLink 与 GPU 中转缓冲路径](nvidia-gds-overview.assets/gds-performance-paths.png)

*原文图 1.1，正文第 6 页 / PDF 第 10 页。红色表示 PCIe 路径，绿色表示 GPU 间 NVLink；GPU A 内的 Buf 展示中间缓冲区。*

动态路由主要针对网络文件系统，例如文中列出的 DDN EXAScaler、VAST NFS 和 WekaFS。目标是减少存储 NIC 与目标 GPU 之间跨 Root Port 传输的代价。

```text
读取配置中的挂载点与存储 NIC 地址
  -> 为挂载点 / 卷预计算距离存储 NIC 较近的候选 GPU
  -> 收到目标 GPU 的读写请求
     -> 若路径已合适：无需动态路由
     -> 若需跨根复合体等代价较高路径：按策略选择中转方式
        -> 例如 NIC -> 邻近 GPU 缓冲区 -> NVLink -> 目标 GPU
  -> 完成最终目标缓冲区的数据传输
```

若有多个候选 GPU，底层文件系统驱动仍需根据 GPU 缓冲区及回调机制选择合适的存储 NIC。写出按相应方向组织数据流。

### 5.3 路由策略与配置

动态路由开关是 `properties.rdma_dynamic_routing`，**默认关闭**。开启后，还需要提供相关存储 NIC 的 IP 地址。策略按配置顺序尝试，先满足条件者优先。

| 策略 | 数据路径 | 主要适用条件 |
| --- | --- | --- |
| `GPU_MEM_NVLINKS` | NIC -> 中转 GPU -> NVLink -> 目标 GPU | 存在与 NIC 同 PCIe 树的中转 GPU，且两个 GPU 之间有 NVLink |
| `GPU_MEM` | NIC -> 中转 GPU -> PCIe -> 目标 GPU | 存在与 NIC 同 PCIe 树的中转 GPU，使用 PCIe 完成 GPU 间复制 |
| `SYS_MEM` | NIC -> 固定 CPU 内存 -> GPU | 使用系统内存中转；原文列举的典型情况是没有 GPU 与存储 NIC 共享 Root Port |
| `P2P` | NIC 与 GPU 之间直接进行 PCIe P2P | 可以跨 Root Port；路径代价可能较高 |

原文默认顺序为：

```text
GPU_MEM_NVLINKS -> GPU_MEM -> SYS_MEM -> P2P
```

配置时还需注意：

- `rdma_dev_addr_list` 可以在全局、文件系统或挂载点层级配置；挂载点级最具体，全局列表用于更具体列表为空时的回退。
- 对同一文件系统，原文明确指出：设置了文件系统级地址列表后，不应同时配置该文件系统的 `mount_table`，否则会被视为配置错误。配置层级不应理解为可以任意重复叠加。
- 同一网络共享对应多个挂载点时，库不能按这些配置区分所有挂载点，会将地址视作一个共享条目；应围绕唯一共享组织配置。
- 如果目标 GPU 与 NIC 已处于合适的同一 PCIe 树路径，开启开关也不会强制进行中转。
- 可以用原文的 `gdscheck -p` 检查开关、策略顺序及挂载点地址是否被识别；这属于配置验证，实际性能仍需观察运行结果。

来源：§1.2.2、§1.2.6，正文第 6-10、12-17 页。

## 6. 兼容模式、内存与直接传输边界

### 6.1 什么时候会使用 CPU 兼容路径

原文列出的情况包括显式配置要求兼容模式、所选挂载点没有 GDS 支持、文件系统无法满足直接 I/O 条件，以及依赖 `nvidia-fs.ko` 的路径缺少该驱动。对于满足条件的新版 NVMe P2PDMA 路径，不能仅因没有 nvidia-fs 就判断必须回退。

兼容模式使用 CPU 系统内存中的非页缓存缓冲和标准 POSIX 调用，不要求 NVFS 内核驱动。它解决的是接口在不支持直接路径的环境下继续工作的需求，不能据此认定已获得 GDS 的直接 DMA 收益。

### 6.2 可以使用 GDS，也不一定一步直达

| 情况 | 原文说明的处理方向 |
| --- | --- |
| 文件偏移、GPU 地址或请求长度不满足 cuFile 块对齐 | 库可以处理，但可能产生额外操作与性能影响 |
| 请求太小，文件系统不能支持 RDMA | 需要额外处理，不能假定直接 RDMA |
| 传输超过 GPU BAR1 aperture 大小 | 库需要处理该限制，不能把整次请求视为单段直达 |
| 最优路径需要通过另一块 GPU / NVLink | 使用中间 GPU 缓冲区进行多阶段传输 |

以上情况并不全部等于“退回完整的 CPU 兼容模式”；应区分直接路径中的分段或 GPU 中转，与通过 CPU 内存的兼容路径。

### 6.3 内存类型

- 原文列出的 GPU 内存分配方式包括 `cudaMalloc`、`cuMemAlloc`、`cuMemCreate/cuMemMap`。
- 也可将 `cudaHostAlloc`、`cudaMallocHost` 分配的 CPU 内存作为 I/O 目标。
- GDS P2P 模式不支持 `cudaMallocManaged` 分配的可迁移内存；在具有 UVM 支持的相关系统上，系统分配的内存（如 `malloc` 或栈内存）也不属于其 P2P 支持范围。原文说明这些分配可以经使用内部 GPU / CPU 中转缓冲区的兼容路径进行 I/O。

来源：§1.1.2、§1.2.3、§1.3.2，正文第 2、10、17-18 页。

## 7. 部署流程与版本条件

### 7.1 部署顺序

以下顺序是对原文部署依赖的整理：

1. **识别目标存储和挂载点。** 确定本地 NVMe、网络或分布式文件系统，以及其 GDS 支持方式。
2. **准备宿主机组件。** 配置 GPU 驱动、相关文件系统和存储驱动；依路径选择 nvidia-fs 或满足条件的 P2PDMA 实现。RDMA 路径还需相应网络软件栈与硬件。
3. **准备用户态库。** 应用使用 `cufile.h` 和 `libcufile.so`；运行时需要 CUDA 驱动库。原文还列出 `libmount-dev`、`libnuma-dev` 等依赖。
4. **配置运行策略。** 按需要设置兼容模式、日志和统计；网络存储若启用动态路由，还要配置地址列表和策略顺序。
5. **核对配置与执行效果。** 使用 `gdscheck -p` 等原文工具检查配置，再结合日志和统计判断路径及瓶颈。
6. **接入应用流水线。** 组织缓冲区、读写顺序和并发，验证完整“读取 -> 计算 -> 写出”过程。

### 7.2 不能忽略的版本例外

| 原文版本条件 | 对理解与部署的影响 |
| --- | --- |
| CUDA Toolkit 12.2 / GDS 1.7.x 起 | 部分未用 `O_DIRECT` 打开的文件，在缓冲区、长度、偏移满足页对齐时，也可走 GDS 驱动的直接路径 |
| CUDA 12.8 起的特定 NVMe 路径 | x86_64 上，本地 NVMe 或通过 DOCA SNAP 的相关 NVMe 场景，可使用 Linux 上游 PCI P2PDMA，无需依赖 nvidia-fs 或定制 nvme 驱动补丁 |
| 上述 P2PDMA 的系统要求 | 需要支持 PCI P2PDMA 的发行版；原文举例为 Ubuntu 上 Linux 6.2 及以上内核，并要求 OpenRM 570.x 及以上和特定注册配置 |
| RAID0、NVMe Multipathing | 原文指出上游 P2PDMA 对这些情况尚未启用，未有专门补丁时不能按普通 P2PDMA 路径处理 |

这些是所提供版本的条件说明，不应简化为“所有 NVMe 都不需要 nvidia-fs”或“只升级 CUDA 就能启用”。

### 7.3 容器部署

容器主要打包应用、头文件和用户态库，仍依赖宿主机提供内核与驱动能力。因此，容器中安装 cuFile 并不能替代宿主机的存储、文件系统或 GPU 驱动配置。

若宿主机缺少相应支持，在兼容模式可用时，应用仍可能继续运行，但实际通过 CPU 内存完成传输。判断部署是否成功，应同时确认功能完成和预期数据路径。

来源：§1.2.3、§1.3.2-1.4.2，正文第 10、17-23 页。

## 8. 监控与排障流程

| 观察手段 | 能看到什么 | 原文限制或要点 |
| --- | --- | --- |
| Ftrace / Tracepoints | 函数调用与执行轨迹 | 原文称 libcufile 有静态 Tracepoints，nvidia-fs 暂不支持此类 Tracepoints；导出函数符号可使用 Ftrace 跟踪 |
| 日志 | 错误、警告和调试信息 | 在 `cufile.json` 中选择 `ERROR/WARN/INFO/DEBUG/TRACE` 等级 |
| Profiling / 统计 | 用于分析功能与性能问题的统计项 | 按配置启用，具体项参考原文指向的排障指南 |
| `gdscheck -p` | 动态路由开关、策略和挂载点 / NIC 地址配置 | 检查配置识别结果，不能单独证明工作负载已经达到预期带宽 |

可按以下顺序理解和排查问题（基于原文能力整理）：

```text
I/O 是否正确完成？
  -> 实际是直接路径、带中转的 GDS 路径，还是 CPU 兼容路径？
  -> 挂载点、驱动、内存类型、对齐与配置是否符合预期？
  -> 是否存在跨 Root Port 的高代价路径？
  -> 应用并发、异步与批处理是否充分利用设备和链路？
```

来源：§1.2.2-1.2.4、§1.2.6.3，正文第 6-11、16-17 页。

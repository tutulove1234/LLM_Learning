可以把 vLLM 的 KV cache 理解成：保存模型已经算过的 token 的 Key/Value，让后续生成不用重复计算。 以下按当前仓库的 V1 架构说明。

1. GPU 上怎么管理：分块，而不是每个请求占一大片连续显存

vLLM 把 KV cache 分成固定大小的 Block（块），按请求需要逐步分配。一个请求的块可以散落在显存中，由 **Block Table（块表）**记录位置。

请求 A：token 逻辑块  [0] [1] [2]
                      │   │   │
块表映射到显存块：   [7] [2] [9]

Attention 根据块表读取 KV

这就是 PagedAttention 的核心思路，类似操作系统的分页：减少连续内存要求和空间浪费。

2. 架构中的主要模块

| 模块 | 简单理解 | 职责 |

3. 存储层级之间怎么管理

默认核心是 GPU 显存；CPU、磁盘和远端缓存需要配置相应后端，并非默认全部开启。

当前仓库的内置多层卸载管理器采用下面的路径：

GPU 显存                 CPU 内存                 次级存储
正在参与计算的 KV  ⇄  卸载缓存 / 中转站  ⇄  文件系统、对象存储、远端
速度最快、容量有限       容量更大                  容量可扩展、延迟更高

- 保存： GPU KV 拷贝到 CPU，再由多层管理器向配置的次级层保存。
- 取回： 次级层命中后，先提升到 CPU，再加载到 GPU，之后才能用于计算。
- 淘汰： 各层按缓存策略回收空间；正在使用或传输的块通过引用计数等机制保护。

这条“CPU 中转”路径对应内置 TieringOffloadingManager；其他 Connector 可以有不同路径，例如在不同实例之间直接传输 KV，用于 Prefill/Decode 分离。

4. 一个请求的完整过程

1. 进入请求： 查找已有前缀 KV；相同前缀命中后可以复用。
2. 开始计算： 为未命中的部分分配 GPU 块，Prefill 写入 KV。
3. 逐 token 生成： Decode 读取历史 KV，并追加新 token 的 KV。
4. 请求结束： 释放块的引用；可复用的前缀可能继续保留，直到空间被回收。
5. 显存不足： V1 可以抢占请求，释放其块，之后重新计算；启用卸载后端后，也可从外部缓存恢复命中的部分。

要区分两个概念：前缀缓存解决“能否少算”，分层卸载解决“KV 能保存在哪里”。
